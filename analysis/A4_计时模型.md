## ★ 与台账冲突：`gdut_hwd` 的"16–20 s/ep"是错的（应为 ≈9）

* 台账 §2b.1 记 `gdut_hwd`（`sgh`/`cg` 族）实测 **16–20 s/ep**，并据此称计时模型"低估小数据集 2.2–2.7×"。
* 底座复算：`sgh_200ep`/`cg_200ep` 共 **12** 条，s/ep = **7.76–11.96**（中位 **8.49**）。
* **台账同一节自己记的 wall/epochs 也给出同一答案**：`wall = 1204/1184/1131/1043/1420/1038 s`、`ep = 121/129/120/120/169/120` ⇒ **8.40–9.95 s/ep**。
* ⇒ 台账的"16–20"与它自己引用的原始数据**自相矛盾**；真值是 **≈8.8 s/ep**。
* **后果**：模型预测 7.3 ÷ 真值 8.8 = **1.21×（模型是准的）**，而不是台账写的 2.2–2.7×（低估）
  ⇒ **"计时模型低估小数据集"这条不得挂在 `gdut_hwd` 上**（`roboflow_hardhat` 一侧 82.5 vs 77.6 = 1.06× 亦为准）。
* 附：`gdut_hwd` 内有 1 个离群点 `sgh_30ep_lr005_s43n` = **26.9 s/ep**（其余 ≤12.3），疑为并发/冷缓存，**做 ETA 取中位不取均值**。

## 登记缺口（不伪造系数）

* 台账用的两系数模型 `s/ep ≈ 2.727e-3·val_imgs + 4.85e-3·train_imgs` **无法在本地重拟合**：
  底座没有 train/val 图数（那在 data yaml 里，未取件；日志里有零散值：`permuted N train im_files` 与 `val: Scanning … N images`，但按 run 归位需要额外解析）。
* ⇒ 本件**只给逐数据集实测 s/ep**（这对 ETA 已经够用），**不给重拟合系数**；如需重拟合，须先补一份 `run → (train_imgs, val_imgs)` 表。
