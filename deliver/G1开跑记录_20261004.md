**★ 启动方式的第二个坑（值得记）**：`ssh` 执行 `setsid nohup ... &` 时，

⇒ 正确写法是**整条命令的 stdout 都重定向掉**：`( setsid nohup ... >log 2>&1 </dev/null & ) >/dev/null 2>&1`。

## 十、监视值守的运行事实（2026-10-04 20:05，round 32）

### 10.1 ★ "两次采样"修复**在生产里验证过**，不只是合成测试

重启后共出现 **3 次单次低显存**（B GPU0 @18:39 为 1 MiB、@19:29 为 4 MiB；B GPU1 @19:52 为 4 MiB），
**每次都被降级为备注**，且在**下一次采样就恢复**（状态文件里 `gpu_idle_0` / `gpu_idle_1` 回到 0）。
⇒ 按旧逻辑，这会是**又 3 条幽灵报警**。修复有效。

### 10.2 ★ 采样混叠（值得记的机制，不是机器行为变化）

监视循环周期 **600 s** 与 B 机 50p 单 run 周期 **≈1500 s** 恰成 **2:5** 关系
⇒ 采样会**每 5 轮落在 run 周期的同一相位** ⇒ 边界空档**反复落在采样点上**（B 机尤甚）。
**这是采样伪影，不是 B 机行为变了。**
⇒ 若以后要更均匀地抓边界，应把周期取成与 run 周期**互质**（如 617 s），而不是整除关系。

### 10.3 ★ SSH 网关压力**有一半是我造成的**

近期约**一半**采样报 `Error reading SSH protocol banner`；但监视器的 4 次重试**每轮都成功，没丢一轮**。
最可能的原因：**我在主会话里额外的手动 SSH 采样**与监视器**争同一个连接预算**
（证据：19:20 我那次 A 机采样失败，而监视器 round 28 在前后一分钟读 A 机正常）。
⇒ **纪律**：云端巡检**交给监视器**，主会话不再随手连；需要时**一次连够**、不反复重连。
