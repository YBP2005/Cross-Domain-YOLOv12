# 训练协议指纹核验 —— `workers=16` / `batch=32` 是否真的贯穿全库

> **触发**：2026-10-02 作者口径纠正
> 「固定 workers=16，batch_size=32。我没有记错的话。**有一些特别早期的不是这样的。其他应该都是。**」
>
> **一句话结论**：**两半都对**。底座 **2276** 个 run **无一例外**是
> `batch=32 / workers=16 / imgsz=640`；确实存在早期偏离件，但它们**全部在底座之外**，
> 且其中绝大多数是**根本没有训练结果的产物目录**。
>
> 证据：`base/args_protocol_snapshot.csv`（7671 条记录，2026-10-02 抓取，**不可再生**）
> 守卫：`scripts/39_verify_protocol_fingerprint.py`

---

## 一、问题为什么重要

论文里所有跨臂比较（§4.2 单调性、§4.3/§4.4 对照、§4.5 普查、A13 同域/跨域）
都默认**两支共享同一训练协议**。若某臂实际是 `batch=4`，那不是噪声，而是
**协议不一致**——BN 统计量与梯度噪声都变了，格内配对不再成立。

而在此之前，这个前提**只被守卫了一半**：底座 `run_table_canonical.csv` 的 `ARGS_KEYS`
里**确实有 `batch` 和 `imgsz`**，但**没有 `workers`**。
也就是说 `batch=32` 一直可从底座自证，而 **`workers=16` 从未有过任何证据**——
作者记忆里那两个量，恰好一个是"有列的"、一个是"没列的"。
本次把两件事都补齐，并且让两条证据路径**互相印证**。

⇒ 它们的 `results.csv` 在两次抓取之间自然长大。**协议字段（`batch/workers/imgsz/epochs/args_bytes`）逐位相同**。
⇒ 快照**不可再生但可复现**：只要机器还在，一条命令就能重建。

> ★ **这次端到端复现测试抓到了一个会静默写坏快照的 bug**（值得记）：
> 采集端只打 **11** 列（不含 `name`），而落盘表头是 **13** 列 ——

> 于是守卫**崩在 `project.startswith`**，而**根因在采集端**，很容易朝错误方向发展。
> 已在 `39b` 里加**写前行宽自检**（行宽 != 表头宽即拒绝落盘，不覆盖好数据）。
> 这正是"生成件写前必须断言自己的输出形状"的又一个实例。

## 三、结论（逐 run 断言，不是只看总数）

**两条独立证据路径**（互不依赖，且本次做了**对撞**核对）：

| 检查 | 实测 |
|---|---|
| **路径 1：底座自带 `batch` 列**（不依赖快照） | **2300** 行有值，其中 **≠32 的 0 行** |
| 底座自带 `imgsz` 列 | 2300 行有值，**≠640 的 0 行** |
| **路径 2：`args` 快照实体记录** | 6379 条，**偏离 32/16/640 的 0 条** |
| **对撞：底座 `batch` 列 vs 快照实体记录** | **矛盾 0 行**；底座有值却无实体记录的 **0 行** |
| 底座 distinct run | **2276**（底座 2301 行） |
| 底座 run 在快照中**缺档** | **0** |
| 底座 run 只有 0 字节占位、无实体档案 | **0** |
| 底座含 Ultralytics 默认名产物 | 0 |
| 底座含外来项目 run | 0 |
| 早期 `workers=8` 基线泄漏进底座 | 0 |

> **`workers` 只有路径 2 能证**——底座没有这一列。
> 这也正是 `args_protocol_snapshot.csv` **不可替代**的原因（`raw/` 里已删件同理）。

## 五、★ 新发现：`/workspace/runs/<name>/args.yaml` 可能是 **0 字节占位**

这是本次踩到的一个真实陷阱，值得单独登记。

A 机上同一个 run 名**可以在三处存在**：

| 路径 | `args.yaml` | `results.csv` | 说明 |
|---|---|---|---|
| `/workspace/runs/<name>/` | **0 字节**（11 例） | 0 或 ~12 KB | **占位**，不可作协议证据 |
| `/workspace/p4_base_weights/<name>/` | 1779 B | 101 行 + `weights/` | 实体 |
| `/workspace/b_archive/runs/<name>/` | 1779 B | 101 行 | 实体（B 机归档） |

实测 11 个 0 字节件（全是 `r10_*_3way_*`，§7 clean 三方协议那一族）：

* 其中 **7 个**同目录 `results.csv` **非空**（~12.1 KB = 101 行），**4 个**连 `results.csv` 也是 0 字节；
* **这 11 个名字在别处各有 3 份健康档案**（A×2 + B×1），**全部是 `32/16/640`** 且 `results.csv` 非空。

⇒ 两条纪律：

1. **`os.path.exists()` 对 0 字节文件返回真** —— 我第一版扫描因此把 0 字节 `results.csv`
   误记成 `has_res=1`，差点写出一个假阳结论。**判"有档案"必须看字节数，不能看存在性。**
2. **0 字节 `args.yaml` ≠ 该 run 没有 args** —— 实体在 `p4_base_weights/` 或 `b_archive/runs/`。
   从 `/workspace/runs/<name>/` 读协议的脚本会**静默拿到空表**。

守卫的口径因此定为：*每个底座 run 必须有 ≥1 条字节数 > 0 的记录，且**所有**字节数 > 0 的记录都必须等于 32/16/640。*

## 六、边界与局限（诚实条款）

1. **快照是时点抓取，不可再生**。pod 是租用的，A/B 机关机后这份现场即消失；
   `base/args_protocol_snapshot.csv` 本身就是交付物。
   若日后新增实验，快照**不会自动增长** ⇒ 守卫对"新增但未入快照"的 run 会报 `E2 缺档`，
   这是**设计意图**（提醒补抓），不是回归。
2. **不覆盖 `momentum` / `weight_decay` / `warmup_epochs`**。
   本次只核了作者点名的 `workers` / `batch`（+ `imgsz`）。
   `run_table_canonical.csv` 的 `ARGS_KEYS` 同样**不含这三项** ⇒
   "momentum=0.925 / wd=1e-4 / warmup=3" 仍是**未经守卫的前提**。
   如需，可按同一快照模式补抓（快照已含 `path`，改脚本一行即可扩展字段）。
3. **`workers` 不影响 mAP**，只影响数据加载吞吐。所以即便有 `workers=8` 的件入了底座，
   也不构成"结论错"；本条守的是**协议自洽**（以及 §十.9/§十.10 的墙钟口径）。
4. 快照**包含 `raw/` 归档 2011 条**，覆盖面超出活机；但归档件不再有机器现场可回溯，
   其 `args.yaml` 字节数来自本地副本。
