# 缺陷记录 ②：汇总查名的改名件盲区（生成器级，2026-10-01）

> **一句话**：`01_build_base.py` 查 test 读数汇总时用的是**磁盘原始目录名**，而汇总记的是**短名**
> ⇒ **所有改名件（`.incomplete_*` / `_PARTIAL_*` / `_oomfix` / `_NNNNNN`）的 test 列恒为空**。
> 这不是"改名件没有 test 读数"，是**键对不上**。修复后全域**只有 1 个格变化**。

---

## 1. 怎么发现的

作者问「D1 的 s50 读数要不要并入底座」。为回答该问题，先核查 canonical 里 s50 两行的状态：

```
b2_smoke2sf_base30_s50n.incomplete_20260924_104028 , archive_snapshot , 30/30 , best 0.38052 , test <空>
b2_smoke2sf_lr005_30ep_s50n.incomplete_...         , archive_snapshot , 30/30 , best 0.42645 , test <空>
```

两行都**跑满 30/30**（故 `ok_outcome()` 判 `archive_snapshot` 可用），只是 test 列空。
顺着查生成器，发现：

```python
s = summary.get(run, {})      # run = 磁盘目录名（带 .incomplete_ 后缀）
                              # summary 的键 = sio 里的短名
```

`run` 带后缀、`summary` 不带 ⇒ **恒查不到**。而 B 侧 `sio_b_results.csv` **本来就有这两行**：

```
b2_smoke2sf_base30_s50n,shapeiou,30,0.6695,0.3806,0.7738,0.6226
b2_smoke2sf_lr005_30ep_s50n,shapeiou,30,0.7261,0.4266,0.8399,0.6557
```

（小数制；D1 归档件 `p1d1_s50_test_readings.csv` 是同一读数的百分数制 `38.0560 / 42.6603`。）

⇒ **D1 的读数其实早已在汇总里**，只是生成器读不到。这也解释了此前"84 个改名件 test 读数全为空"的普查结论
——那个结论的**成因判断是错的**（不是缺读数，是查不到）。

## 2. 修复

```python
_RS = re.compile(r'(_PARTIAL_\d+|\.incomplete_\d+_\d+|_oomfix|_\d{6})$')
s = summary.get(run, {})
if not s:
    # 不区分机器：作者裁定「跨机可以默认和同机一样，跨机不存在差异」
    s = summary.get(_RS.sub('', run), {})
```

顺带修第二处同源缺陷：`also_on_other_machine` 原先也只比**原始名**，
而两机对同一 run 的改名时间戳必然不同 ⇒ 改名件永远"看不到对岸"。
已补短名索引（两边任一命中即算跨机重名）：**50 → 76** 行被正确标记。

## 6. 本轮踩到的坑（记录以免复犯）

1. **手改了生成件**：先手工把 A5 的符号改对，随后重跑生成器又把它覆盖回旧值。
   ⇒ **生成件只能改生成器**。已改为修 `06_A25.py`（含 `per_seed[30]-per_seed[200]` 这个
   **真正的算错处**，此前只改了硬编码字符串，没改计算式）。
2. **heredoc 把 `\n` 折成真换行**：在 heredoc 里用 `\\n` 写出的补丁，落到目标文件时变成真换行，
   造成 `SyntaxError: unterminated string literal`。⇒ 生成器补丁改用**多次 `w(...)` 调用**，
   不在字符串里塞换行。
3. **Windows Python 看不到 bash 的 `/tmp`**：比对脚本一度把所有文件报成 NEW。
   ⇒ 备份要拷进仓库目录再用。
4. **补丁脚本崩溃在 `print` 上**：控制台是 GBK，`print` 中文/`−`号抛 `UnicodeEncodeError`，
   而写文件在最后一行 ⇒ **整个补丁静默不生效**。⇒ 补丁脚本一律先
   `sys.stdout.reconfigure(encoding='utf-8', errors='replace')`。

## 7. 新增守卫：跨件一致性（防这类漂移再发生）

第 5 节的漂移能发生，是因为**稿内数字与生成件之间没有机械检查**。已在 `16_draft_tag_paths.py`
新增**跨件一致性守卫**：**从 `A9`/`A13`/`A18` 生成件里解析**数字，再断言稿内出现同一字面量。
任一侧更新而另一侧没跟上即报红；**一件都解析不到也报红**（空集合硬失败，经验 #56）。

| 生成件里的值 | 检查 |
|---|---|
| §4.5 端点差总数（轮数 45 + 标签 16 = **61**） | 稿内 `61 paired endpoint differences` |
| §4.5 轮数轴过闸门 **20** 条中负向 **17** | 稿内 `20** clear that gate and **17 of them` |
| §4.5 标签轴过闸门 **8** 条 | 稿内 `8** clear it and **only 2` |
| §4.5 独立组/配对 **22 / 14** | 稿内 `22 groups (14 independent pairs)` |
| §4.5 跨域格数 **128** | 稿内 `over 128 cross-domain cells` |
| §8 `dota15` 格数 **32** | 稿内 `out of 32 and 8` |

**阴性对照（现场做过）**：把稿内四处改回旧值（61→60、20/17→18/15、128→127、32→31），
守卫**四处全报红**；还原后 6 项全绿。

> 守卫自身也犯过一次错：标签轴总数一度抓成"过闸门 8 条"而非"可报 8 + 不可报 8 = 16"，
> 导致误报漂移。⇒ 解析型守卫必须**先跑一次全绿**确认它不是在空转/错抓。
